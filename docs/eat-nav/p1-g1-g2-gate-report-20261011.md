## Source audit: logical step ordering

The historical runner source was read from the original stopped-container P1 run and preserved [read-only](/home/kojima/eatnav-experiments/p1-long-horizon-v1/static-audit/p1-paired-source-original.py). Its SHA-256 is `1205147f7c63ed2e91d6981868f639f48af90f3ea6d692862f9f76713cca46b9`. In commit `67a1acf`, the bridge source shows the following serial protocol:

1. `eat_nav_sim_clock_bridge.py:182-188` handles a `step` request by calling `clock(ns)`, then `poses(..., ns)`, then `wait_command(ns)`. `clock():67-75` advances protocol state, clears the previous commands, publishes `/clock`, and waits until the ROS clock has the requested stamp. `poses():86-95` publishes TF with that exact stamp.
2. `eat_nav_exact_stamp_bridge.py:15-38` accepts a follower command only if its stamp is current, TF has the current stamp, Path has been published, the branch has not already supplied a command, and values are finite. `eat_nav_command_delivery_bridge.py:157-174` waits for all branches and records the command it adopts.
3. The preserved simulator source at lines 376-397 awaits the initial bridge response and injects accepted commands into the command manager. For each subsequent step, lines 486-503 await the next-stamp bridge response and inject commands. The next loop iteration records the current command at lines 421-449 and calls `env.step(action_batch)` at line 456. The synchronous TCP request in `phase_c_bridge_client.py:14-20` does not return until the bridge replies. Thus, for each completed historical iteration, the causal order is `/clock → TF → follower command → bridge acceptance → command injection → physics`.
4. `p1_statistical_pilot.py:36-44` checks bridge freshness and equality of command, clock and TF stamps. The P1 derivative's `accepted_events()` at preserved source lines 196-202 additionally requires five accepted branch events, including the monitor branch, at the same stamp. The exact-stamp follower also checks the returned TF stamp and emits at most once per logical stamp. This is a **source-level guarantee for completed 120-step P1 iterations**; it is not evidence of a successful 600-step run.

The existing runner cannot satisfy G2 unchanged. Its line 87 rejects `diagnostic_control_steps != 120`. It holds the trace in memory at line 409 and writes the four JSONL traces only after the loop at lines 506-511, conflicting with from-first-write durable raw logging. More seriously, the unchanged RL cfg sets `episode_length_s = 20.0` in `velocity_env_cfg.py:409`; `envs.py:40-65` automatically resets a timed-out env within `env.step()`. A 600 × 50 ms preflight crosses that boundary around step 400. The preserved runner then marks the branch ended and stops appending its trace at lines 459-473 while the bridge's old Path may remain active. Merely changing `120` to `600` would neither preserve 600 records nor establish a single-episode Path/command contract. These are prelaunch protocol blockers, recorded in [G2 stop evidence](/home/kojima/eatnav-experiments/p1-long-horizon-v1/static-audit/g2-not-run.json). No G2 Path was published.
