# 車体速度入力のFAST-LIO化：ユーザー指示による変更

## 決定

車体移動の速度入力は車輪回転換算から、FAST-LIOの `/Odometry`（大文字O、`nav_msgs/msg/Odometry`）由来へ変更する。クローラ関節回転速度とサブクローラ状態は引き続き別入力として保持する。goalや未来観測を入力しない方針、単一DEM、14候補、物理・制御周期、精度基準は変更しない。

実機のtwistが有効か、frame_id/child_frame_id、基準位置、実更新周期・取得/受信遅延は未確認。topicの存在だけで速度取得済みとは扱わない。twist未設定のゼロを停止として使用しない。有効twistなら規定車体軸・基準点へ変換し、未提供なら過去poseの片側差分を検討する。後者には実timestampを使い、t0より未来またはt0後に受信した観測を使わない。欠測時の車輪速度への無印の代用は禁止する。

## シミュレータでの扱い

現収集には20Hzのroot位置・姿勢・速度と関節状態を保存しているため、元記録を保持して車体速度入力を再構築できる。現行rawのstate[18]は車輪換算速度であり、この値をFAST-LIOと呼び替えない。

シミュレータ内の初期検証では車体運動に基づく理想オドメトリを使用する案とする。これは実FAST-LIOの処理実行・ノイズ・遅延・退化を再現したデータではない。教師と入力で同時刻の真値を使う理想条件では、実機適合・同等精度を主張しない。基準点/座標変換、利用速度成分、マスク、スキーマと取得元タグを確定し、旧入力と区別する実装・検証を行ってから学習を再開する。

実機仕様を確認せずに架空の遅延やノイズを実機相当として確定しない。実FAST-LIOをシミュレータで走らせる場合はLiDAR等の追加計算が必要で、今回の大量点群を収集しない方式とは別案となる。

## 実行保全

収集workerは現行条件で継続し、生のroot/joint/command/DEM記録を保存する。自動workflowの親プロセスのみSIGSTOPで保留し、旧車輪オドメトリ入力によるdataset化・学習への自動移行を止めた。実機操作およびR6再開は行っていない。状態記録はローカルデータrootの `fast-lio-policy-change.json`。再開前に実行プロセスと新入力の検証結果を確認する。

## 並列数と速度

選定並列数は10環境。trainの各cellは10台、validation/final_testは14試行を10台+4台に分けるため、常時10台とは限らない。各台の速度上限は0.30m/sだが、headingに応じた減速・旋回時の並進停止があり、実速度は地形・滑り・Actor出力で変化する。各2秒区間で停止・リセットしない。

物理dt=0.005s、制御dt=0.05s、DEM更新4Hz。壁時計倍率を1倍に固定していない。既存benchmarkの10台×10秒は起動/観測/保存を含む約89秒だったため、少なくともその測定で各台が実時間より高速だったとはいえない。10台並列による総収集量と、各台の実時間倍率を区別する。
