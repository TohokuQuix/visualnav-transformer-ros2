**Status:** Audit only. No reference training, shortcut ablation, simulator smoke, state selection or formal rollout has started. The [proposed config](phase-c-config.yaml) is for review; it has not been used by a runner.

## 1. Checkpoints and frozen inputs

[Checkpoint audit](checkpoint-audit.json) verified the two available EAT/NoMaD pilot checkpoints and all three frozen Phase B GT evaluators. The original Quality-enabled checkpoint is `fcaf3b93…`, and the Quality-disabled baseline is `c8187d5b…`. Both used **4,096 train / 512 validation windows**, reached the **8-epoch cap**, and their final epoch was a new validation best (loss 0.3221 and 0.3152 respectively). Both contain EMA and optimizer state, have the frozen split hash, and use context size 3, four DEM frames, 8 XY-delta points at 0.25 s, 20×20 DEM and 10-step DDPM. The disabled checkpoint has no quality token. The prior training entrypoint initializes from scratch when `resume=None`, but the checkpoint does not itself record a warm-start flag; strict proof of that invocation is unavailable. Specialized small-pair overfit checkpoints are not reference candidates. The repository also contains a 76.5 MB legacy image-NoMaD weight (`nomad.pth`, SHA `70f79b82…`), but its RGB EfficientNet/image-goal encoder is incompatible with the EAT DEM/relative-goal reference and the scratch condition.

**Decision:** No existing checkpoint meets the formal reference condition. Phase C-0 training is required. The Quality-disabled `c8187d5b…` checkpoint remains suitable only for the later load/generation/connection smoke. The intended formal generator is the unchanged `EATNav` DEM CNN, goal token, 4-layer Transformer, `ConditionalUnet1D` and DDPM scheduler, with Quality disabled and scratch weights. The proposed training seed is 123, maximum 100 epochs, patience 10, minimum delta 0, batch 64 and LR 1e-4. Best EMA would be selected solely by aggregate validation diffusion loss. If validation is still improving at the cap, Gate C0 is inconclusive and formal rollout will not begin.

The existing `train_eat_nav.train()` constructs `EATDataset` over **all** valid windows, including padded partial futures. Phase C-0 therefore needs a complete-only index view; simply calling that entrypoint without a filter would violate this brief. The frozen complete-only counts are **49,598 train / 6,171 validation / 6,208 held-out**, while Phase B aligned labels use 49,576 / 6,164 / 6,208 after excluding 29 terminal endpoint windows. These are different documented window sets. The training view must keep split seed 123, **recompute action statistics from complete-only train**, and preserve held-out isolation. The old 8-epoch checkpoint statistics used all valid train windows, including padded futures (416,944 valid trajectory steps, ECDF count 55,358), so copying those values would breach the Phase C-0 complete-only recipe. Existing `save_checkpoint` stores weights, EMA, optimizer, normalization and split metadata, but **does not store RNG state or an LR scheduler state**. The Phase C-0 runner needs a separate atomic latest/resume artifact containing CPU/CUDA/Python/NumPy RNG states, sampler position and software provenance. No LR scheduler is currently configured; none should be added to the model recipe.

[Source SHA audit](source-sha-audit.json) matched the manifest, relative labels, Phase A Probe code, and all three aligned NPZ files. The three frozen GT evaluator checkpoints match their Phase B training summary SHA. The RL checkpoint SHA is `b789f3ab…`. Phase B Evaluator weights, target standardization and predictor ensemble remain unchanged.

## 2. Generator output and follower path

`EATNav.sample()` produces **cumulative robot-local XY waypoints**, shape `[batch,8,2]`, after denormalizing XY deltas. The existing ROS helper `metric_path()` prepends the current origin, transforms local XY by observed pose/yaw into `map`, and emits a `nav_msgs/Path` with **9 poses** for an 8-point candidate when metric scale is 1.0. `navigate_robot.py` publishes `/teaching_playback/path`; the separate ROS2 `simple_trajectory_follower` subscribes there, transforms into `chassis/body`, and emits `/cmd_vel_auto` (`TwistStamped`) at 20 Hz under the Onix config. It retains path and controller state across updates; an empty Path is ignored. Its lookahead, turning, progress and stuck-recovery state must be fresh or replicated identically for each branch.

**Missing connection:** The current simulator collector drives a 6-D RL Actor action directly. There is no present bridge from the follower's `/cmd_vel_auto` to the simulator's `base_velocity` command manager and then through the frozen Actor to the six joint actions. Phase C must implement and test this bridge after approval, without changing the RL Actor, robot dynamics or follower logic. ROS2 process/topic, TF, `/clock`, command timing and a fresh controller state per candidate need verification. A numerical imitation of the follower would not establish that the actual follower was exercised.

## 3. Same-state branch feasibility

The existing 100-env collection config assigns **distinct generated terrain tiles, command streams and initial-condition streams** to each env. It cannot supply eight identical terrain branches as-is. The preferred prototype is eight synchronized simulator clones with identical terrain mesh/seed/difficulty and copied root pose/velocity, joint state and controller/action state, then candidate-specific paths. This avoids relying on an undocumented full PhysX snapshot API. It remains a **proposal**, not a demonstrated restore method; branch equality and duplicate-rollout variation are explicit C1 tests.

The simulator code adds state beyond root/joints: per-env `_latency_substeps`, `_onix_latency_seconds`, `_latency_policy_obs_prev`, reset mask, and each action `DelayBuffer` ring contents/pointer/push counts; flipper action `_previous_targets`, `_travel_direction`, processed actions; command sampler RNG/held command/time-left; ActionManager last action; episode/progress tracking; DEM/raycast and contact sensor state; CPU/CUDA/NumPy/Python RNG. IsaacLab `ObservationManager.compute_group()` applies noise **before** clip/scale, and `OnixManagerBasedRLEnv.step()` then applies policy-observation latency. Calling observation compute twice would advance noise RNG and can change the policy input. Initial state capture must instrument a **single** observation pass, retain raw term values and post-noise/pre-delay values, and save the actual post-delay `obs["policy"]` delivered to the Actor. The pre-noise hook and exact state-copy API are not yet implemented or proven. PhysX warm-start/contact caches may still cause residual branch variation even when visible state matches; the required duplicate test will quantify it.

The saved RL Actor takes **22-D policy observation** and has hidden widths 1024/512/256 with ELU. The 256-D input to `actor.6` is the action-head-preceding latent; a forward pre-hook can capture it while preserving the exact deterministic `act_inference()` call. `empirical_normalization: false` in the RL config. The Critic takes **267-D** `obs["critic"]` and outputs (V_0); this group contains privileged height scan, contact and latency terms. Checkpoint-specific toggles are last action **off**, joint effort **on**, policy height scan **off**, action and policy-observation latency **on**. Exact field order and term dimensions should be dumped from the live `ObservationManager` and saved in smoke. The Actor latent can likely be captured online, but exact pre/post noise and action consistency remain unproven until smoke.

## 4. Runtime and capacity estimate

The previous unchanged 100-env collector ran 3,600 control steps in **3,865.73 wall seconds**, about **1.07 s per 100-env vector step**, and wrote **377 MB** compressed for 360,000 robot steps. This is not a benchmark for eight cloned branches plus ROS follower; it only gives an order-of-magnitude bound. Current hardware is RTX 5070 Ti **16,303 MiB** (15,711 MiB free at audit), 94 GiB RAM (89 GiB available), and **2.5 TB** free disk. Container software is Python 3.11.13, PyTorch 2.7.0+cu128, CUDA 12.8, diffusers 0.35.1, NumPy 1.26.0 and Isaac Sim 5.1.0-rc.19.

| Work | Preflight estimate | Basis / uncertainty |
|---|---:|---|
| Reference Phase C-0 training | **2–12 h**, 2–10 GiB GPU, 0.5–3 GiB artifacts | 49,598/6,171 windows are ~12× the 4,096/512 pilot per epoch; stop epoch unknown. No epoch wall time or training VRAM was saved for the pilot, so these are planning ranges, not measurements. First approved short timing probe must refine them before long training. |
| 1 state × 8 candidates | **0.5–6 min**, up to simulator+ROS startup | Eight-way synchronized 40-step branch is likely faster than eight serial 40-step runs. The 100-env pilot's 1.07 s/step is only a rough upper reference; clone/follower costs are unmeasured. |
| 64 states × 8 candidates | **1–12 h** plus development/smoke, 4–12 GiB GPU, 0.2–3 GiB logs | 20,480 candidate control-step records, plus duplicate repeats on ≥10% states, observations, state snapshots, and atomic resume files. Variability is dominated by branch implementation and simulator speed. |

The first-approved smoke must record wall time, GPU peak, serialized bytes, and 1-state×8 extrapolation. Unexpected major growth stops work for review. The proposed formal set is 64 terrain-stratified states and (K=8), with diffusion seeds 1001–1008; these are **proposals only** and would be frozen before formal results. New terrain seeds must be checked disjoint from Phase A/B seed sets. Phase C must provide one externally specified relative goal shared by all eight candidates, never derive it from a generated endpoint. No future outcome may enter state selection.

## 5. Approval boundary and next evidence

After first approval, the order is Phase C-0 reference training (or a short timing probe followed by it), G/GTE/GTS/GT shortcut diagnostic, branch/controller/observation logging implementation, consistency tests, then a few-state smoke. Formal 50–100-state rollout still requires **second approval** after reporting reference convergence, state equality, duplicate variation, exact Actor/latent capture, end-to-end follower control and revised resource estimate. No Phase B retraining, full collection, Phase D/E or real-robot test is authorized here.
